# PowerShell Execution Model — PRF Knowledge Base (v0.1.0)

Authoritative background for AI agents that generate PowerShell. Read alongside the PRF rule categories: **COMP-** (compatibility), **SAFE-** (safe mutation), **ERR-** (error handling), **IDEM-** (idempotency), **SEC-** (security). Statements hold for both Windows PowerShell 5.1 and PowerShell 7.x unless a version is called out explicitly.

## 1. Why PowerShell defeats models trained on bash

bash composes text: programs emit bytes and pipes carry lines. PowerShell composes objects: cmdlets emit full .NET objects with types, properties, and methods, and rendering happens only at the pipeline terminus (`Out-Default`), never in between. A model that treats a pipe as text filtering writes PowerShell that looks right, parses cleanly, and quietly discards the structure that makes PowerShell dependable.

| Aspect | bash | PowerShell |
| --- | --- | --- |
| Pipeline payload | Rendered lines of text | Live .NET objects with typed members |
| Filtering | `grep` over bytes | `Where-Object` over properties |
| Sorting and counting | `sort`, `wc -l` | `Sort-Object`, `Measure-Object` on named properties |
| Failure signal | Exit code plus stderr bytes | Six numbered streams carrying typed `ErrorRecord` objects |
| Command chaining | `&&` everywhere | `&&` only in PowerShell 7+ (parse error in 5.1) |
| String comparison | Case-sensitive | `-eq`, `-match`, `-replace` are case-insensitive by default; prefix `c` (`-ceq`) forces exact case |

### Side-by-side: hunting errors in a log

```powershell
# Bash reflex — functional, but you are scraping rendered text:
Get-Content .\app.log | findstr err
# PowerShell-native — every hit is a MatchInfo object:
Get-Content .\app.log | Select-String -Pattern 'err'
# Structure survives the pipe, so follow-ups stay precise:
$hits = Get-Content .\app.log | Select-String -Pattern 'FATAL'
"Found $($hits.Count) FATAL lines; first one is line $($hits[0].LineNumber) in $($hits[0].Path)"
```

`findstr` output is anonymous text: no line numbers, no file attribution, no recount without re-parsing. `Select-String` exposes `Path`, `LineNumber`, `Line`, and `Pattern` as properties, which turns log analysis from scraping into querying. The gap between "syntax translated" and "data model translated" is where most COMP- defects are born.

Bash instincts that recur in generated code:

| Generated by bash instinct | What PowerShell actually does |
| --- | --- |
| `curl https://api -o out.json` | In 5.1 `curl` aliases `Invoke-WebRequest`, which has no `-o` (it takes `-OutFile`); the alias disappears in 7.x, so the same token flips meaning across versions. |
| `ls` filtered through `grep` | Stock Windows has no `grep`; the native tool is `Select-String`, and `ls` is really `Get-ChildItem`. |
| `step1 && step2` | Parse error on 5.1; on 7.x `&&` chains on native exit codes, not on cmdlet success — pair it with the discipline in section 4. |
| `rm -rf ./build` | Becomes `rm -r -fo ./build`: permanent deletion, no recycle bin, no undo — a SAFE- red flag deserving `-WhatIf` scaffolding. |

## 2. Approved Verb-Noun naming

Names follow `ApprovedVerb-SingularNoun` (`Get-Service`, never `GetServices` or `Fetch-Services`). `Get-Verb` lists the sanctioned set; unapproved verbs still execute but raise warnings on `Import-Module` and break discoverability conventions. The core verbs carry contracts that generators must not blur:

| Verb | Contract | Typical misuse |
| --- | --- | --- |
| `Get` | Retrieves data; must cause no side effects | `Get-Thing` that also writes config files |
| `Set` | Establishes or replaces the complete state of an existing resource | Using `Set` to append incrementally (that is `Add`) |
| `New` | Creates a new resource; typically fails when it already exists | Using `New` where reruns require converging `Set` semantics |
| `Add` | Appends a resource to a container, preserving contents | Using `Add` to "ensure desired state", stacking duplicates on every retry |
| `Remove` | Deletes a resource from a container | Wildcard removal with no `-Confirm` support |
| `Invoke` | Performs a synchronous operation | `Invoke-Thing` that only reads data |
| `Test` | Validates and returns `$true`/`$false`, mutating nothing | A `Test-Path`-style function that creates directories as a side effect |

Rerunnable automation wants `Set`-style convergence: the second execution must reach the same state as the tenth. Append-style `Add-Content` loops and duplicate-hostile `New-Item` calls are recurring IDEM- findings; prefer `Set-Content` for whole-file rewrites and `New-Item -Force` only when overwrite is genuinely intended.

## 3. The six output streams

Every cmdlet writes to numbered streams; only stream 1 carries "the result":

| Stream | Name | Writer | Visible by default |
| --- | --- | --- | --- |
| 1 | Success / output | `Write-Output` and bare expressions | Yes |
| 2 | Error | `Write-Error` | Yes |
| 3 | Warning | `Write-Warning` | Yes |
| 4 | Verbose | `Write-Verbose` | No; needs `-Verbose` or `$VerbosePreference` |
| 5 | Debug | `Write-Debug` | No; needs `-Debug` or `$DebugPreference` |
| 6 | Information | `Write-Information`, and `Write-Host` since 5.0 | `Write-Host` yes; `Write-Information` no |

Redirection operators truncate their target by default; doubling the arrow appends (`>>`, `2>>`, `*>>`):

```powershell
.\build.ps1 1> build.log 2> build.err.log    # split success from error
.\build.ps1 *> build.all.log                 # capture all six streams
.\build.ps1 6> ui.log                        # isolate Write-Host / information traffic
$merged = & git.exe describe --tags 2>&1     # fold error into success for one capture
.\build.ps1 > build.log 2>&1                 # one file for both streams; order matters
```

Details generators miss:

- Pointing streams 1 and 2 at the same file with two separate operators (`1> f 2> f`) collides on the file handle; merge first (`2>&1`), then redirect.
- Under 5.1, `2>&1` around a native executable wraps stderr lines as `ErrorRecord` objects with encoding artifacts; 7.x delivers plain strings. Any parser of merged output must accept both shapes.
- `Write-Host` stopped being console-only in 5.0: it rides stream 6, so transcripts and `6>` captures record it. Never route secrets through any of these writers (SEC-016).
- `*>` sweeps verbose and debug chatter into the log too; oversized noisy logs are a review smell, and debug output can leak internal detail.

## 4. Error semantics

Two failure classes with opposite physics:

| Property | Non-terminating error | Terminating error |
| --- | --- | --- |
| Remaining input keeps processing | Yes | No; the pipeline unwinds immediately |
| Caught by `catch` | No — unless `-ErrorAction Stop` promotes it | Yes |
| `$?` afterwards | `$false` | `$false` |
| Logged to `$Error` | Yes | Yes |
| Typical sources | Per-item cmdlet failures (one locked file in a batch) | `throw`, runtime exceptions, cmdlet internals |

`$ErrorActionPreference` (EAP) governs non-terminating errors: `Continue` (default — print and proceed), `SilentlyContinue` (suppress), `Inquire` (prompt), `Ignore` (suppress, not even stored in `$Error`), `Stop` (promote to terminating), `Suspend` (workflow plumbing), and `Break` in recent 7.x builds (drop into the debugger). PowerShell scoping is dynamic, so an EAP set in a caller is inherited by every callee: `$ErrorActionPreference = 'Stop'` at the top of a script rewrites error law for every function and module it touches, converting expected per-item misses into aborting exceptions, while setting EAP inside a function confines the change to that function and its callees — restore it in `finally` either way. Crucially, EAP never applies to native executables: a failing `git.exe` ignores every preference value (7.3+ adds opt-in throwing via `$PSNativeCommandUseErrorActionPreference`), so only `$LASTEXITCODE` reports native failure reliably.

Because most state-changing cmdlets fail non-terminatingly, a bare `try/catch` around them is decoration: the failure bypasses `catch` and the script strolls onward across a half-mutated system — simultaneously an ERR- and an IDEM- defect:

```powershell
# BROKEN: Set-Content fails non-terminatingly; catch never fires; restore never runs.
try { Set-Content -Path C:\cfg\app.ini -Value $config } catch { Restore-Backup }

# RIGHT: promote the failure so the handler actually owns it.
try {
    Set-Content -Path C:\cfg\app.ini -Value $config -ErrorAction Stop
} catch {
    Restore-Backup
    throw
}
```

Working rule: every mutating cmdlet inside a `try` block gets `-ErrorAction Stop`, and batch mutations loop explicitly so one poisoned item neither aborts the batch nor vanishes silently — both outcomes are SAFE- findings.

Native executables answer to two different signals:

| Signal | Type | Updated by | Reliable for |
| --- | --- | --- | --- |
| `$?` | Boolean | Every pipeline — cmdlet or native (`$true` when no error occurred / exit code 0) | Cheap "did that work" branching |
| `$LASTEXITCODE` | Integer | Native executables only; cmdlets leave it stale | Authoritative native exit-code handling |

```powershell
ping.exe contoso.com -n 1        # native: refreshes BOTH $? and $LASTEXITCODE
Get-ChildItem C:\logs            # cmdlet: refreshes $?, leaves $LASTEXITCODE untouched
$LASTEXITCODE                    # still ping's exit code — a classic stale read

git pull --rebase
if ($LASTEXITCODE -ne 0) { throw "git pull failed with exit code $LASTEXITCODE" }
```

## 5. Automatic variables cheat sheet

| Variable | Meaning | Generator hazard |
| --- | --- | --- |
| `$_` | Current pipeline object inside `process` blocks and scriptblocks | Reading it outside a live pipeline yields stale or `$null` data |
| `$Matches` | Hashtable from the last successful `-match`; key `0` is the whole match, named groups by name | A failed match leaves the previous groups in place; trust `$Matches` only inside the success branch |
| `$MyInvocation` | How the current script or command was invoked (names, line, position text) | Inside a function, `.MyCommand.Name` names the function, not the script |
| `$PSScriptRoot` | Folder holding the executing script; empty at the interactive console (PS3+ anywhere) | Empty-string concatenation corrupts paths — always build with `Join-Path` |
| `$LASTEXITCODE` | Exit code of the most recent native executable | Goes stale after cmdlets; see section 4 |
| `$null` | The singleton null value | Comparison operand order changes semantics — see below |

`-eq` is overloaded. With a collection on the left it becomes a filter returning matching elements, not a boolean verdict. Keeping `$null` on the left forces scalar comparison no matter what the right-hand expression produced:

```powershell
$items = @()                                  # imagine an upstream filter emptied this
if ($items -eq $null) { 'was null?' }         # FILTER mode: no element equals null, nothing comes back
if ($null -eq $items) { 'definitely null' }   # scalar comparison: deterministic

if ('Release-2024.10.01' -match 'Release-(?<ver>[\d.]+)') {
    $Matches.ver                              # 2024.10.01 — meaningful only inside this branch
}

$configPath = Join-Path -Path $PSScriptRoot -ChildPath 'settings.psd1'
"Launched $($MyInvocation.MyCommand.Name) from $($MyInvocation.ScriptName)"
```

## 6. Formatting gotchas

`Format-Table` and `Format-List` do not decorate objects — they consume them and emit opaque formatting records. Everything downstream of a `Format-*` cmdlet manipulates rendering metadata, not your data:

```powershell
# BROKEN: by the time Sort-Object runs, no real WS property exists anymore.
Get-Process | Format-Table Name, WS | Sort-Object WS -Descending

# RIGHT: shape the data first; format last, at the terminal edge.
Get-Process | Sort-Object WS -Descending |
    Select-Object -First 5 -Property Name, WS |
    Format-Table
```

`Select-Object -First N` is not a display hint: since PS3 it halts the upstream pipeline after N items. Two consequences matter to generators. First, the ordering bug: truncate-then-sort keeps an arbitrary subset and sorts only that subset. Second, partial application: truncate-then-mutate applies the change to just N items — occasionally deliberate batching, frequently a latent IDEM- defect where the author meant "show five". When a cap precedes a mutating cmdlet, make it loud and intentional.

Calculated properties synthesize members inline; `Select-Object` and the `Format-*` cmdlets both accept them:

```powershell
Get-ChildItem $env:TEMP -File |
    Sort-Object Length -Descending |
    Select-Object -First 5 Name,
        @{ n = 'SizeMB';  e = { [math]::Round($_.Length / 1MB, 2) } },
        @{ n = 'AgeDays'; e = { ((Get-Date) - $_.LastWriteTime).Days } }
```

## 7. Scoping, `$using:`, and splatting

Scopes nest. Child scopes read parent variables, but assignment creates a local copy (copy-on-write), so naive writes evaporate. Dot-sourcing (`. .\shared.ps1`) executes in the current scope instead — handy for shared helpers, hazardous when scripts spray variables into their host:

```powershell
$x = 1
function Set-LocalCopy { $x = 99 }             # writes a function-local shadow
Set-LocalCopy
$x                                             # still 1
$script:RunCount = 0
function Add-RunCount { $script:RunCount++ }   # $script: targets the script scope
Add-RunCount; Add-RunCount
$script:RunCount                               # 2
```

Variables never flow automatically into remote sessions or background jobs. The `$using:` modifier captures the caller's value and ships it over; what arrives is a serialized copy — a property bag, not the live object. `ForEach-Object -Parallel` (7.0+) follows the same `$using:` convention alongside `$_`:

```powershell
$logFilter = '*.etl'
Invoke-Command -ComputerName SRV01 -ScriptBlock {
    Get-ChildItem C:\logs -Filter $using:logFilter
}
Start-Job -ScriptBlock { Get-ChildItem C:\logs -Filter $using:logFilter } | Wait-Job | Receive-Job
```

Splatting binds a hashtable as named parameters with `@name` (not `$name`) and is the cleanest way to assemble arguments conditionally or forward `$PSBoundParameters` through wrapper functions:

```powershell
$requestParams = @{
    Uri         = 'https://api.contoso.com/v2/deploy'
    Method      = 'Post'
    ContentType = 'application/json'
}
if ($dryRun) { $requestParams.Method = 'Get' }
Invoke-RestMethod @requestParams -ErrorAction Stop
```

## 8. `begin` / `process` / `end` in advanced functions

A function using `[CmdletBinding()]` or any `[Parameter()]` attribute is advanced and may divide into three blocks: `begin` runs once before input arrives, `process` runs once per pipeline item (with `$_` and bound parameters populated), and `end` runs once after the last item. This is the single most common structural failure in generated PowerShell: a function without a `process` block executes exactly once regardless of pipeline input, so it sees only the final item — or must resort to lazy `$input` enumeration.

```powershell
function Convert-ToNormalizedPath {
    [CmdletBinding()]
    param(
        [Parameter(ValueFromPipeline)]
        [string]$Path
    )
    begin   { $count = 0 }
    process {
        $count++
        $Path.Replace('/', '\').TrimEnd('\')
    }
    end     { Write-Verbose -Message "normalized $count path(s)" }
}

'C:/apps/service', 'C:\tools\' | Convert-ToNormalizedPath
```

Checklist for generated advanced functions: declare `ValueFromPipeline` only when a `process` block consumes it; treat `$_` as undefined in `begin` and `end`; expect per-item writers such as `Write-Verbose` and `Write-Warning` to repeat once per item; accumulate totals in variables declared in `begin` and reported in `end`.

## 9. Implications for AI generators

- **COMP-** — Treat every bash idiom as guilty until proven innocent: colliding aliases (`curl`, `sort`), `&&` absent before 7.x, case-insensitive default operators, text-versus-object pipelines. Emit full cmdlet names in delivered scripts; reserve aliases for interactive typing.
- **SAFE-** — Assume every mutating cmdlet fires by default: attach `-WhatIf`/`-Confirm` awareness, explicit `-ErrorAction Stop`, and preflight `Test-*` guards; give wildcard-plus-`Remove-*` combinations their own review pass.
- **ERR-** — `try` without `-ErrorAction Stop` on state-changing cmdlets is theater; `$LASTEXITCODE` read after a cmdlet is a stale artifact; parsers of `2>&1` output must tolerate the 5.1 ErrorRecord shape and the 7.x string shape alike.
- **IDEM-** — Convergence dies quietly: `-First N` ahead of a mutation half-applies changes, stacked `Add-*` calls defeat rerun equality where `Set-*` would converge, and format-before-action pipelines destroy the data needed to detect remaining work.
- **SEC-** — All six streams are capture surfaces feeding transcripts and redirected logs, verbose and debug traffic included. Never interpolate secrets into command lines, never compose code strings for `Invoke-Expression`, and move credentials across `$using:` boundaries only deliberately.

Internalize sections 1 through 8 and most of the defects these rule categories police simply stop being generated; when in doubt, choose the boring explicit form — full cmdlet names, `-ErrorAction Stop` on mutations, `$null` on the left, formatting last.
